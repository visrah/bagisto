# Absa / Fiserv payment integration boundary

## Current architecture

No Absa/Fiserv specification or credentials are present in this task. No endpoint, signing algorithm, parameter name, sandbox URL, MUR acceptance or refund capability is assumed here. Do not enable a payment method until those details are confirmed by the acquiring bank for this merchant's contract.

Bagisto 2.5.x-dev discovers methods through the `payment_methods` configuration. A gateway package extends `Webkul\Payment\Payment\Payment`, declares its own code/class and contributes merchant fields through `Config/system.php`. `getRedirectUrl()` supports a redirect flow. Existing implementations in Stripe, Paypal and PayGlocal show provider registration, callback routes, order/invoice handling and tests. Checkout collects totals, validates the cart and asks the selected method for a redirect before creating an offline order. The gateway must therefore define when it creates a pending order and reserves inventory, rather than assuming core has already done it. Invoice and refund repositories own the accounting and stock events; gateway code must not patch totals or order status columns directly.

## Required bank handoff

Obtain the exact product name and API/version specification, merchant onboarding instructions, supported transaction currencies including MUR, settlement currency, sandbox test accounts/cards, production activation process, credential types and rotation process, hosted checkout/redirect flow, server verification/query interface, callback authentication and replay rules, authorization versus capture semantics, timeout/cancellation behaviour, duplicate request rules, reconciliation exports, and refund/partial refund support. Credentials must be supplied through a secret manager or deployment environment, never a commit, chat log, fixture or browser payload.

## Implementation sequence after that handoff

1. Create an isolated payment package following the existing Payment provider/configuration pattern. Register the provider without altering existing method codes or public checkout APIs. Add only configuration fields the bank specification requires; explicitly select sandbox or production with an allowlisted environment, never a merchant-supplied arbitrary API URL.
2. Use platform-managed environment secrets where practical. If merchants enter secrets through the admin, use authenticated configuration writes with encryption at rest and masked reads; the current generic configuration store is not evidence of encrypted credential storage. Implement encryption and rotation before accepting live gateway secrets. Exclude secrets, signatures, cardholder data and raw gateway payloads from logs, API responses and frontend configuration.
3. Validate that the contract accepts MUR and the order's currency. Convert Bagisto's decimal amount using the specification's exact amount representation and rounding rules, never binary floating point arithmetic for signing or requests. Keep the order currency and amount immutable for the payment attempt.
4. Persist a payment attempt with a unique internal identifier and gateway reference where supported. Snapshot amount, currency, order/cart reference, environment and expected operation. Lock the cart/order while initiating so repeated submissions reuse the attempt. Never use a user's order identifier as proof of ownership.
5. Initiate hosted checkout or redirect exactly as specified. Keep card entry on the provider's supported hosted surface where available. Return and cancel URLs carry an opaque attempt reference; a browser return is not proof of payment.
6. Verify payment server-side using authenticated callbacks and/or the documented verification interface. Compare merchant account, environment, reference, amount, currency and final capture state to the stored attempt. A timeout or unknown state remains pending and enters reconciliation; it must not become paid or cancelled merely because the customer closed the page.
7. Add a narrowly scoped callback route outside customer login. Exempt only that exact route from CSRF if the documented server callback requires it. Authenticate raw callback bytes using the specified verification mechanism before processing. Reject forged, mismatched, stale or replayed messages according to the bank rules. Do not weaken existing admin authentication or authorization.
8. Enforce idempotency with unique attempt/event references and transactional order locks. Record an event once, allow documented out-of-order delivery, and create at most one paid invoice for the same capture. PostgreSQL conflicts must use upsert/constraints with the correct transaction design rather than catching a failed insert inside an aborted transaction. Retries must not charge twice or reserve stock twice.
9. On verified capture, call the existing invoice pipeline with the appropriate state and quantity. Preserve partial capture semantics if supported. On verified failure/cancellation, use existing cancellation and stock-release transitions only when the bank guarantees there is no successful capture. Never infer payment from fulfilment.
10. Implement refunds only if the merchant contract and API support them. Keep a refund request pending until verified, apply idempotency to full and partial refunds, and call Bagisto's refund workflow exactly once. Verify whether Bagisto's selected refund path returns money remotely or only records an offline refund; do not advertise automatic bank refunds until tested.
11. Add a scheduled reconciliation task for pending/unknown attempts and missed callbacks, with bounded retries and a merchant-visible action needed state. Log only safe attempt identifiers, status transitions and redacted error classifications.

## Acceptance tests

Use specification-derived fixtures and the real sandbox: successful MUR payment, declined payment, customer cancellation, browser return before callback, callback before return, double-click, parallel initiation, duplicate callback, out-of-order callback, wrong amount/currency/account/environment, invalid signature, replay, network timeout after initiation/capture, session expiry, abandoned cart, concurrent stock changes, full/partial refund if supported, refund retry and credential rotation. Verify invoice, order, inventory, customer ownership and reconciliation outcomes in each case. Production activation requires bank approval and a controlled real transaction/refund where authorized.

## Implemented: Absa Spark hosted checkout (`packages/Webkul/AbsaSpark`)

The Absa Spark (Fiserv Checkouts) client was copied into the project as `Webkul\AbsaSpark`, so there is no private Composer dependency and no Saloon; it uses Laravel's HTTP client. It is built from the vendor's own client code, not a bank specification, and has only been run against a local stub that checks the request signature, never against Absa's sandbox.

- **Flow:** cart, checkout, Place Order. The Absa payment method's redirect URL is `absa-spark/pay`, which locks the cart, creates the order (this checks and reserves stock under row locks, and a shortage returns the customer to the cart before Absa is called), sets it to Pending Payment, saves an `absa_payments` row and creates the hosted checkout, then redirects to Absa. Absa's webhook (`POST absa-spark/webhook`), the customer's return (`absa-spark/return/{ulid}`) and a scheduled reconcile all feed one settle step that asks Absa for the real state; neither the browser redirect nor the webhook payload is trusted.
- **Approved:** the approval must match the stored checkout id, store id, transaction type, amount in cents and currency; the order then moves to Processing with one paid invoice and transaction. A payment Absa takes after the order was cancelled is recorded and flagged on the order as needing a refund, not invoiced.
- **Declined, cancelled or expired:** the order is cancelled, which returns the reserved stock. A customer returning from a failed payment gets their cart back, only in the browser session that started the payment. `absa-spark:reconcile` runs every minute through the scheduler, checks pending payments older than 5 minutes, expires those older than 30 and re-checks expired ones for 7 days.
- **Currency and amounts:** MUR only. The method is hidden unless the shop's base currency is MUR. Amounts are whole cents (an integer) everywhere internally and converted to a two-decimal value only for Fiserv.
- **Credentials:** Settings, Absa Spark (`admin/settings/absa-spark`, ACL key `settings.absa_spark`): enabled, checkout name, sandbox or live, store ID, API key and secret. The key and secret are stored encrypted in `core_config` (Bagisto's own `password` field type only masks the input and stores plain text), are never sent back to the browser, and a blank field keeps the saved value. A migration grants the permission to an existing Shop owner role. `ABSA_SPARK_BASE_URL` overrides the Fiserv address, for a stub.
- **Operations:** the webhook address must be public HTTPS and is shown on the settings page. The scheduler must run (`php artisan schedule:run` each minute) for reconciliation.
- **Switch:** Absa can be turned on or off without touching the saved credentials, from the Enable field on its settings page or from the switch on the Payments page (`PUT admin/settings/absa-spark/toggle`, same ACL key). Turning it on is refused until the store ID, key and secret are saved, and a switched-off method is not offered at checkout.
- **Verified:** 62 package tests (client signing, request body and retries, the flow, settlement, reconcile, settings, switch, access) with a faked Fiserv, and a browser run against a signature-checking local stub: pay, webhook confirms, order Processing with a paid invoice; decline, order Cancelled, stock returned, cart restored.
